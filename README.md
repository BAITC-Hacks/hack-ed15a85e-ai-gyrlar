# StockPilot

Локальное приложение для расчёта пополнения склада и проверки заказов поставщикам. Решение кейса «Автоматизация формирования заказов поставщикам» для Электрокомплект, HackAlem AI.

Hackathon team repository for AI GYRLAR.

Менеджер загружает продажи, остатки и ожидаемые поставки, проверяет разовые всплески и получает рекомендации по товарам. Из рекомендаций создаются отдельные заказы поставщикам: их можно сохранить, изменить, выгрузить в Excel, отметить размещение и получение. ИИ-агент объясняет расчёт и сравнивает сценарии. Отправку заказа поставщику выполняет менеджер.

## Быстрый запуск

Откройте **START.cmd**. Приложение откроется по адресу **http://127.0.0.1:8765**. При первом запуске с `data/dataset.json` используются данные партнёра; затем приложение запоминает выбранный набор. Этот файл локальный и не переносится при клонировании Git-репозитория.

На другом компьютере нужен Python 3.10 или новее:

```sh
python -m pip install -r requirements.txt
python app.py
```

Если `data/dataset.json` отсутствует, приложение автоматически использует небольшой синтетический набор. Для принудительного демо:

```sh
python app.py --demo --port 8766
```

`START.cmd` использует Python из установленной среды Codex, если он доступен, иначе `py -3`. `launcher.py` запускает сервер в фоне и открывает браузер. Для остановки удобнее запускать `python app.py` в терминале и нажать Ctrl+C. Сервер доступен только на 127.0.0.1. Это приложение для одного пользователя, не публичный production-сервер.

## Путь от файлов до заказа

1. На **главной** нажмите **«Загрузить продажи»** или перетащите Excel/CSV. На странице **«Данные»** есть отдельные загрузки и образцы для продаж, свободных остатков и товаров в пути.
2. В окне импорта выберите лист, дату расчёта и соответствие столбцов. Нажмите **«Применить и пересчитать»**. Затем добавьте остатки и, если есть ожидаемые поставки, товары в пути.
3. Откройте **«Проверка всплесков»** и отметьте обычный спрос или разовые проекты. В **«Анализе продаж»** нажмите на товар: карточка показывает график, исходный и регулярный спрос, остаток, поставки и формулу заказа.
4. Проверьте **«Параметры расчёта»**, включая условия отдельных поставщиков. Выберите товары в анализе и нажмите **«Сформировать заказы»**. Если товары не выделены, используется текущий фильтр.
5. В **«Сохранённых заказах»** проверьте количество и дату поступления, сохраните черновик и выгрузите XLSX или CSV. После фактического размещения у поставщика отметьте заказ как размещённый; после поступления — как полученный.

Можно пройти весь путь на синтетике через **«Попробовать тестовый пример»**. Заказы, параметры и правки у демо, данных кейса и пользовательских загрузок сохраняются раздельно.

## Три источника: Excel или CSV

При ручной загрузке поддерживаются `.xlsx` и `.csv` до 20 МБ. Первая строка содержит названия столбцов. В браузере можно выбрать один лист и вручную сопоставить любые заголовки; другие листы этого файла не импортируются. Образцы CSV из раздела «Данные» совместимы между собой и открываются в Excel.

| Источник | Обязательные поля | Что происходит при обновлении |
| --- | --- | --- |
| Продажи по операциям | Код товара, дата продажи, количество | История заменяется, а не прибавляется к прошлой загрузке |
| Продажи по месяцам | Код товара, столбцы месяцев (`2026-01`, `Январь 2026`) | Аналогично; полная история предпочтительнее прироста за один месяц |
| Свободные остатки | Код товара, остаток | Полный снимок заменяет предыдущие остатки; у отсутствующих товаров остаток становится **неизвестным**, а не нулевым |
| Товары в пути | Код товара, количество, дата поступления | Полный снимок заменяет предыдущие внешние поставки; для отсутствующих товаров список поставок пуст |

Сопоставление выполняется по **поставщику и коду товара**. Если поставщик не указан в столбце, можно задать его для всего файла. Без поставщика совпадение только по коду разрешено, когда оно однозначно. Неизвестные товары, неоднозначные коды и ошибочные строки блокируют весь импорт с пояснением; сначала добавьте товар в историю продаж. Похожие названия не используются для объединения. Текстовые коды с ведущими нулями и числа с десятичной запятой поддерживаются.

В остатках можно указать дату снимка, название, единицу, кратность и минимальную партию (MOQ). Дата остатка не должна быть позже даты расчёта. Без даты принимается выбранная дата расчёта с предупреждением — это допущение, а не подтверждение свежести выгрузки. Одинаковые повторные строки остатков не суммируются, противоречащие значения отклоняются. Новая загрузка остатков также заменяет ранее внесённые ручные остатки и результаты локальной приёмки; загружайте актуальный полный снимок, включая нулевые значения.

В поставках поддерживаются несколько дат поступления одного товара и разные заказы на одну дату. Укажите **номер заказа поставщику**, чтобы различать поставки и сопоставлять их с сохранёнными заказами StockPilot. Повтор одной комбинации «товар + номер заказа + дата» отклоняется. Просроченные поступления сохраняются для сверки, но не уменьшают потребность. Для полного снимка без поставок допустима строка известного товара с количеством `0` и датой снимка. Единицы в остатках и поставках должны совпадать с продажами.

Продажи также могут содержать остаток и одно ожидаемое поступление на товар. Повторяющиеся значения такого снимка не складываются; для нескольких поступлений используйте отдельный источник «Товары в пути». При последующем обновлении продаж в пользовательском наборе **отдельно загруженные** снимки остатков и поставок сохраняются для совпавших товаров вместе с исходными датами. Новые товары требуют соответствующих остатков; сохранённый старый снимок автоматически свежим не становится. Если новая история не содержит товары из действующих заказов, импорт отклоняется: восстановите их в файле или сначала отмените соответствующие заказы.

Без остатка программа анализирует спрос, но не рассчитывает количество заказа. Остаток можно подтвердить в карточке товара. Без кратности рекомендация предварительная: используется единица. Кратность `0` в продажах считается неизвестной с предупреждением; в отдельном снимке остатков указывайте положительную кратность. Поставка без даты, если она пришла из совмещённого файла продаж, не вычитается из потребности; отдельный импорт поставок требует дату.

Для помесячных продаж распознаются повторная шапка «Количество» и явно подписанные итоги без кода; число исключённых служебных строк показывается. Это поддерживает исходные месячные выгрузки IEK и Systeme Electric. Пропуски месяцев внутри периода файла считаются нулевыми продажами: нужна полная история, желательно за 12–24 месяца. Текущий и будущие месяцы исключены из прогноза. Для нового файла сезонность нейтральная, сведения о периодах отсутствия товара не предполагаются. Лимиты: 250 000 строк, 10 000 товаров, 240 столбцов, 10 листов.

Происхождение отдельного источника сохраняется: файл, лист, время загрузки, дата расчёта, число строк, контрольная сумма и предупреждения. Исходный Excel не изменяется. Последний пользовательский набор, параметры, заказы и правки хранятся в `data/uploaded-state.json`; выбранный набор — в `data/active-dataset.json`. На главной можно вернуться к данным кейса или последней загрузке. Для чтения `.xlsx` и экспорта заказов в Excel нужен `openpyxl` из `requirements.txt`; CSV работает без него.

## Условия поставщиков и проверка всплесков

В **«Параметрах расчёта» → «Условия отдельных поставщиков»** задаются срок поставки, цикл пересмотра заказа и страховой запас в днях. Пустое поле использует общую настройку. Если есть правило категории, его срок или запас имеют приоритет над условием поставщика; цикл заказа берётся из условия поставщика либо общей настройки. Начальные `30 / 14 / 7` дней — редактируемые допущения, их нужно заменить согласованными условиями.

Экран всплесков показывает месяц, фактические продажи, оценку регулярного спроса, причину обнаружения и количество заказа до/после решения. Решение применяется к **обнаруженному всплеску товара за месяц**: «Обычный спрос» сохраняет исходный объём, «Разовый проект» использует регулярную оценку, «Автоматически» следует общему переключателю очистки. Весь месяц не обнуляется. Выбор и время изменения сохраняются; решение можно пересмотреть. Разности заказов между разными строками нельзя складывать: изменения взаимодействуют через тренд и округление.

## Сохранённые заказы и история

Черновики создаются отдельно для каждого поставщика. Заказ содержит номер, дату, ожидаемое поступление, позиции, количества, расчётные основания, предупреждения и историю изменений. Пока количество включено в действующий черновик, оно резервируется при создании новых черновиков — повторное нажатие не создаёт такой же заказ.

- **Черновик:** можно изменить количества, примечание и дату поступления. Количество проверяется по кратности и минимальной партии; `0` исключает позицию из закупки. Если изменился расчёт, перед размещением нужно проверить и сохранить черновик заново.
- **Размещён:** после подтверждения количества учитываются как ожидаемая поставка и уменьшают новые рекомендации в пределах расчётного горизонта. Для размещения нужны актуальные остатки и кратность. Это запись о решении менеджера, **не отправка письма, заявки или заказа через API поставщика**.
- **Получен:** подтверждает полное получение заказа. Менеджер должен подтвердить, что текущие остатки актуальны и ещё не включают эту поставку. Количества добавляются к локальным остаткам, поставка убирается из ожидаемых. Повторная приёмка запрещена; частичная приёмка пока не поддерживается.
- **Отменён:** отменённый черновик освобождает резерв, отменённый размещённый заказ больше не учитывается в пути. История остаётся доступной.

Каждый заказ выгружается в XLSX или CSV с кодами, количеством, единицами и обоснованием. Общий расчёт из анализа также можно выгрузить в CSV. Экспорт сам по себе не меняет статус. Если заказ затем появится во внешней выгрузке товаров в пути, передайте его номер `SP-…` в поле «Номер заказа»: приложение сопоставит обязательство, чтобы не прибавить ту же поставку повторно. Без такого номера связать внешний и локальный заказ надёжно нельзя.

## Регулярное обновление из папки

Сначала **один раз загрузите свои продажи вручную**, чтобы перейти в пользовательский набор: автоматическая загрузка продаж не заменяет демо или данные кейса. Затем в разделе **«Данные» → «Обновление по расписанию»** задайте абсолютный путь к папке и частоту проверки. Папка должна существовать. Выгрузки создаются учётной системой или менеджером; прямого подключения к 1С нет.

```text
C:\Закупки\Выгрузки\
    sales.xlsx       история продаж
    stock.xlsx       полный снимок свободных остатков
    transit.xlsx     полный снимок ожидаемых поставок
```

Вместо `.xlsx` можно использовать `.csv`. Нужен не более чем один файл каждого типа: одновременно `sales.xlsx` и `sales.csv` — ошибка. Имена не зависят от регистра; другие файлы игнорируются. Для автоматической загрузки нужен **один непустой лист и распознаваемые заголовки из образцов**. При ручной загрузке в браузере, в отличие от расписания, лист и соответствие заголовков выбирает менеджер.

Содержимое проверяется по SHA-256: неизменившиеся источники не импортируются повторно. Изменённые продажи заменяют историю, сохраняя отдельно загруженные остатки и поставки для совпавших товаров с их исходными датами. Удаление файла из папки **не удаляет** ранее загруженный источник. Все обнаруженные изменения применяются вместе: ошибка любого файла сохраняет предыдущие данные и показывается в статусе обновления.

Пустой путь в настройке означает только пересчёт текущих данных. Можно включить использование сегодняшней даты; оно не меняет дату ранее загруженного остатка. Кнопка **«Обновить сейчас»** запускает проверку сразу. Статус показывает последнее/следующее обновление и ошибки; сообщения о значимых изменениях видны в приложении. Расписание работает для **активного набора, пока запущен сервер StockPilot**. Закрытый или выключенный компьютер не выполняет задания; фоновой системной службы, email-уведомлений и внешнего планировщика нет.

## Проверка качества прогноза

На странице **«Качество прогноза»** запускается скользящая проверка на последних завершённых месяцах. Для каждого проверяемого месяца прогноз строится только по предшествующей истории, затем сравнивается с исходными фактическими продажами. Рядом рассчитывается простой ориентир — обычное среднее до 12 предыдущих месяцев. Для каждой пары «товар + проверяемый месяц» требуется хотя бы шесть последовательных месяцев истории; пропущенные пары показываются отдельно.

Результаты содержат **MAE** (среднюю абсолютную ошибку в единице товара) и **WAPE** (сумму абсолютных ошибок, делённую на сумму фактических продаж). Чем ниже, тем лучше. При нулевом факте WAPE не определён. Показатели разделены по единицам измерения: метры и штуки не суммируются. Отчёт показывает месяцы, покрытие данных и примеры наиболее крупных ошибок в каждой единице.

Это оценка упрощённого прогноза наблюдаемых месячных продаж. Чтобы не использовать сведения из будущего, здесь не применяются готовая сезонность поставщика, очистка накладных по всей истории, ручные решения о всплесках, компенсация отсутствия товара и бизнес-прирост. Месячная очистка и тренд используют только доступную к тому моменту историю. В проверяемом факте сохраняются разовые проекты, а отсутствие товара может скрывать реальный спрос. Остатки, цены, поставки и сроки не участвуют: отчёт **не доказывает экономию или точность количества заказа**, и алгоритм может оказаться хуже простого среднего на конкретной выборке.

## Подключение настоящего ИИ-агента

1. Скопируйте `.env.example` в `.env`.
2. Укажите свой `OPENAI_API_KEY`. Не отправляйте ключ в чат и не включайте его в репозиторий.
3. При необходимости измените `OPENAI_MODEL`. По умолчанию `gpt-5-mini`.
4. Перезапустите сервер. В интерфейсе появится «ИИ подключён».

Используется Responses API с function calling. Модель выбирает функции `inventory_summary`, `find_products`, `explain_product`, `data_quality`, `simulate_scenario`, получает результаты и формирует ответ. Функции не изменяют заказ и не отправляют сообщения поставщикам. Сценарный расчёт выполняется на копии параметров.

Типовые вопросы о срочных закупках, всплесках, точном артикуле и сценарии роста получают короткий ответ непосредственно из расчётного движка без обращения к API. В чате они отмечены «ПО РАСЧЁТУ». Свободные вопросы обрабатывает языковая модель: по умолчанию ответ рассчитан на 50–100 слов; подробности можно запросить явно. Передаются последние четыре сообщения, цикл ограничен тремя обращениями к модели. Результаты функций кешируются в памяти до изменения данных, параметров, заказов или ручного утверждения; устаревший ответ не попадает в новый расчёт.

Контрольный замер на синтетических данных: ответы о приоритете закупки и товаре занимали 37,7 и 34,2 секунды; после добавления готовых расчётных ответов — менее 0,01 секунды на сервере. Один свободный вопрос с настоящей моделью занял 3,9 секунды и дал ответ в 86 слов. Это отдельные замеры, а не гарантия времени ответа для любых данных или нагрузки API.

При подключённом API в OpenAI передаются вопрос, краткая история чата и результаты выбранных функций: сведения о товарах, количества, источники и замечания. Исходные Excel-файлы не загружаются. Установлено `store=false`; это параметр хранения ответа, а не обещание полного отсутствия обработки данных провайдером. Ключ используется только сервером.

Без ключа доступны ответы «ПО РАСЧЁТУ» и **демо-помощник по заданным сценариям**, а не языковая модель. Демо-помощник поддерживает качество данных и «Срок поставки 45 дней». Демо-режим явно обозначен. Цикл вызова функций проверен с имитацией транспорта; подключение API дополнительно проверено на синтетических данных.

Официальная документация: [Function calling](https://developers.openai.com/api/docs/guides/function-calling), [GPT-5 mini](https://developers.openai.com/api/docs/models/gpt-5-mini).

## Загрузка предоставленных данных

Установите библиотеку чтения Excel, если её нет:

```sh
python -m pip install -r requirements.txt
```

Можно импортировать два архива напрямую:

Либо расположите распакованные каталоги `IEK` и `Systeme electric` внутри одной папки. Вложенные папки из исходных архивов допустимы. В каждом каталоге ожидается шесть файлов: динамика продаж, месячные продажи, месячные остатки, сезонность, товар в пути, MOQ.

```sh

```

Перезапустите приложение после импорта. Описание полей и полноты набора: [data/README.md](data/README.md). Интерфейс показывает источник данных, число товаров и файлов, фильтры поставщика, категории и статуса; экран источников содержит отдельную сводку по каждому поставщику.

Обработанный файл, локальные правки и утверждения исключены из Git. `data/local-state.json` хранит правки, заказы и параметры реальных данных, `data/demo-state.json` — отдельное состояние демо. При повторном запуске консольного импортера ручные остатки сохраняются, но их дата остаётся видимой; менеджеру необходимо сверить их заново. Загрузка нового снимка остатков через интерфейс или папку расписания, напротив, заменяет ручные остатки актуальным снимком.

Не включены 9 документов других типов. 21 319 месяцев по SKU сверились с месячными продажами в пределах допуска; у 8 344 имеются расхождения. В файле поставок IEK повторяются 7 кодов; у повторных строк нет количества поставки.

| Месячные продажи обоих поставщиков | Основной объём спроса, пустые значения внутри отчётного периода трактуются как отсутствие движения |
| Динамика продаж | Проверка накладных на разовые всплески и сверка месячных итогов |
| Месячные остатки | История доступности и предварительный остаток на начало сентября |
| Ведомость Systeme Electric | Свободный остаток на 22.09.2026, категории, артикулы, поставка на 24.09; рост из ведомости для сверки |
| Путь IEK | Поступления с датами 30.09, 01.10, 10.10 и 15.10.2026 |
| Сезонность | 12 предоставленных итоговых коэффициентов из L11:L22, нормированных к среднему 1 |

Ключ — код 1С вместе с поставщиком. Артикулы хранятся строками. Не объединяем товары по похожему названию. Итоговые строки Excel не становятся товарами. Месячные продажи и динамика **не складываются**. Если по коду нет месячной истории, доступные месяцы динамики с 2025 года используются как резервный источник.

Важные ограничения данных:

- Нет ID клиентов. Проверка концентрации одному клиенту реализована в расчётном модуле и проверена на синтетике; на реальных выгрузках доступны только накладные. Номер накладной не считается ID клиента.
- Нет точных интервалов stockout. Пустой или нулевой остаток на начало месяца сам по себе не подтверждает длительность отсутствия. На реальных данных компенсация не выдумывается.
- Для IEK остаток относится к началу сентября. Для части Systeme Electric вне актуальной ведомости также используется месячный снимок. Пустые остатки остаются неизвестными: для таких товаров `qty=null`.
- Сентябрь 2026 неполный и исключён из обучающей истории при исходной дате сценария 22.09.2026. Дату можно изменить в настройках, но это не делает исходные снимки остатков свежими.
- Сезонность предоставлена на уровне поставщика и рассчитана по денежным продажам. Это приближение для количества по SKU, а не подтверждённая индивидуальная сезонность.
- Условия поставщиков по срокам, цикл заказа и запас не представлены. 30/14/7 дней — редактируемые допущения. Категории SE есть, но нормативов по ним нет; правила категорий задаёт менеджер. Для IEK категория неизвестна.
- В SE есть исторический коэффициент роста. Он показан в карточке для сверки, а не применяется повторно поверх собственного тренда. Внешний прогноз прироста задаётся отдельным параметром.
- Расчёт общий по Алматы. Нет надёжной согласованной разбивки свободных остатков обоих поставщиков по каждому складу.
- Товары с закупкой бухтами и учётом в метрах требуют сверки единиц. Упаковка из имени товара автоматически не извлекается.
- Нет валидированного маппинга импорта в конкретную конфигурацию 1С. CSV содержит код 1С и количества, но готовый обмен с 1С не заявляется.

## Методология

1. **Накладные.** Строки одного товара и документа в один день объединяются. Для минимум восьми положительных наблюдений вычисляются медиана `m` и медиана абсолютных отклонений `MAD`. Если объём больше `max(6m, m + 8 × 1.4826 × MAD)`, он заменяется медианой. При переданном обезличенном ID второй проход проверяет суммарный объём клиента за день. Повторяющиеся большие продажи не удаляются просто из-за своего размера.
2. **Сверка.** Из месячных продаж вычитается только избыток выявленных накладных и только при согласованности динамики с месячным итогом: отклонение не больше `max(1, 5% месячного объёма)`. Иначе месяц остаётся по сводному источнику, расхождение показывается.
3. **Месячный контроль.** Второй консервативный фильтр сравнивает десезонализированный месяц с предыдущими 12 месяцами, требует минимум шесть положительных наблюдений и тот же порог. Он также покрывает историю без подробной динамики. Это эвристика; менеджер может подтвердить разовый проект или сохранить исходный спрос через экран проверки всплесков.
4. **Stockout.** При точных интервалах спрос делится на долю доступных дней, увеличение ограничивается трёхкратным уровнем. Полностью недоступный месяц восстанавливается из медианы доступных месяцев с учётом сезона. Нулевые месяцы без подтверждённого stockout остаются нулевыми.
5. **База.** До 24 полных месяцев используются для истории. Последние максимум 12 после появления ненулевого спроса усредняются с линейными весами от старого к новому. Промежуточные месяцы без продаж сохраняются.
6. **Тренд.** Медиана последних трёх десезонализированных месяцев сравнивается с предыдущими тремя. Изменение должны поддерживать минимум два месяца. Берётся половина относительного изменения с ограничением ±30%. Сценарный прирост менеджера применяется отдельно.
7. **Потребность.** Прогноз разворачивается по календарным дням с коэффициентом соответствующего месяца. Горизонт — срок поставки + цикл пересмотра. Страховой запас равен спросу на следующие заданные дни. Это покрытие в днях, а не статистическая гарантия уровня сервиса.
8. **Поставки.** Учитываются только ожидаемые поступления внутри горизонта, начиная с даты расчёта. Просроченные, слишком поздние и поставки без даты не уменьшают потребность. Отдельная ежедневная проекция выявляет дефицит до поступления: поздняя поставка не устраняет уже возникший дефицит.
9. **Заказ.** `net=max(0, demand+safety−free_stock−eligible_transit)`. При `net>0`: `order=ceil(max(net,minimum)/pack)×pack`. При нулевой потребности минимум не создаёт заказ. Разные единицы не складываются в общий объём.
10. **Утверждение и документы.** Исходная рекомендация и ручное количество различаются. Ноль — допустимая ручная корректировка. Неизвестный/устаревший остаток не позволяет утвердить строку или разместить заказ до сверки. Подпись параметров и расчёта снимает старое утверждение при изменениях. Черновики резервируют количества от повторного создания, размещённые заказы добавляют ожидаемые поступления. Финальное решение локальное, автоматической отправки нет.

## Проверка требований

```sh
python -m unittest discover -s tests -v
```

Тесты покрывают влияние остатка и пути, сезонность, рост, категории и условия поставщиков, пропуски, stockout, всплески и ручные решения, раздробленные клиентские продажи, MOQ и кратность, срок поступления, нулевую потребность и утверждение строк. Отдельные проверки охватывают объединение трёх источников, атомарность ошибок, повторные импорты, сохранённые заказы и переходы статусов, приёмку, сверку ожидаемых поставок, экспорт XLSX/CSV, локальное автообновление, хронологическое разделение данных при проверке прогноза и цикл ИИ-агента с имитацией API. Синтетический набор демонстрирует аномалии и известный stockout, которых нельзя достоверно разметить в реальных выгрузках.

Автоматические тесты проверяют корректность правил; оценка на истории запускается отдельно в интерфейсе. Экономия и снижение дефицита в реальном бизнес-процессе не измерялись. Для пилота нужны подтверждённые разовые проекты, периоды наличия, актуальные условия поставщиков и проверка результата на новых периодах. Авторизации, разграничения доступа и общего сервера для нескольких пользователей пока нет; перед публичным размещением они необходимы вместе с подходящим сервером и эксплуатационной настройкой.

## Сценарий показа на защите

1. На главной покажите понятный путь «данные → спрос → заказ». В разделе «Данные» покажите три источника и скачайте совместимые примеры.
2. На примерах загрузите продажи, остатки и товары в пути, проверьте сопоставление столбцов. В материалах кейса покажите фильтры IEK / Systeme Electric и ограничения источников.
3. В «Проверке всплесков» сравните заказ до/после и переключите обнаруженный месяц между разовым проектом и обычным спросом. Для наглядного всплеска можно выбрать тестовый пример.
4. Откройте карточку товара: история, очистка, остаток, даты поступлений и формула. Нажмите «Объяснить с агентом»: короткий ответ помечен «ПО РАСЧЁТУ». Затем сравните «Сценарий роста 20%». Для ответа языковой модели задайте свободный вопрос или попросите подробное объяснение.
5. В параметрах измените срок одного поставщика и пересчитайте рекомендации. Сформируйте отдельные черновики по поставщикам, проверьте количество и выгрузите Excel.
6. На тестовом наборе отметьте размещение заказа и покажите уменьшение новой потребности. Подтвердите полное получение с ещё не включающим поставку остатком и покажите историю статусов.
7. Запустите «Качество прогноза», объясните MAE/WAPE и сравнение с простым средним без обещаний гарантированной экономии.
8. Покажите настройки папки и кнопку «Обновить сейчас». Объясните, что расписание работает при запущенном приложении и ошибочная выгрузка не заменяет текущие данные.
